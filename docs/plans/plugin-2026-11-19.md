## §V. The product, in J's words

- "If I tell people they can use it just the exact same as Auto-Key, where they just put it on a track and then it spits out the BPM and key. Except you can say send BPM and send Auto-Tune."

- Where each piece fits:
  - A downloaded file goes in the app window.
  - Something playing on YouTube while it records in Pro Tools gets the key from the menu-bar toolbar.
  - A file in the session gets the plug-in on its track.

So the main screen is: **key + BPM, and two buttons: SEND BPM and SEND AUTO-TUNE.** Everything else (top-3 keys with %, tuning cents, ×2 / ÷2, pin) is one click away, never on the main screen.

## §L. Licence findings (the recon's open question, answered by reading, no email)

**The answer in three lines**
1. Yes: a free AGPL plug-in can ship as AAX. The AAX SDK carries a GPLv3 option in its own licence file, and GPLv3 §13 / AGPLv3 §13 allow the two to be combined.
2. If JUCE is used, the licence that fits is JUCE's own AGPLv3 option ($0, no tier). JUCE itself lists its bundled AAX SDK as "Proprietary Avid AAX License/GPLv3".
3. The native-shim route (Artemis's) uses no JUCE at all, so there is no JUCE licence to hold. Both routes are legal; licence does not pick the architecture, engineering does (§A).

## §A. Architecture

**The answer in three lines**
1. Artemis's pattern, not Zeropoint's: one native C/C++ core plus three thin hand-written shims (AU, VST3, AAX), no JUCE.
2. The face is SwiftUI, hosted by each shim, sharing Swift files with the app (key spelling, Auto-Tune hand-off, house kit). SEND BPM goes through the app's existing Send to DAW.
3. Code lives in this repo: `core/` (shared, later also the app's engine) and `plugin/`. One `VERSION`, one installer, universal bundles (arm64 + x86_64), macOS 12.0 minimum.

### A1. What the two shipped plug-ins teach

From Zeropoint (JUCE) [disk: its `CLAUDE.md`, `.claude/rules/*.md`, `pluginval-and-signing.md`, `ship-gates.md`, `CMakeLists.txt`]:
1. A pluginval pass can hide skipped work. At strictness 10 the VST3 validator step was skipped (binary not on the Mac) and auval is a no-op for a VST3 target, so "the AU has never been through pluginval at all". Our gate must prove each validator ran.
2. No trailing slash on the pluginval path (it finds zero plug-ins and fails falsely).
3. A build never writes into system plug-in folders. Install is the installer or a named install step.
4. Anything written into a bundle after signing breaks the seal and the host skips it silently. Sign last, then `codesign --verify --deep --strict` inside the build.
5. The AAX signature is verified after signing, every time; the installer refuses an unsigned AAX. `ditto`, never `cp -R`, for AAX bundles.
6. Remote checks on Sofia go through `~/.claude/scripts/ssh-rc` (plain ssh there returns 0 whatever happened).
7. Live caches its plug-in scan (full quit and relaunch); older copies in `/Library` shadow newer ones.
8. Installers put everything system-wide, plain payloads, no postinstall (J's ruling 2026-09-10).
9. J's Live is Live 10, x86_64 only [disk: `lipo -archs` today]. The Intel slice matters on the MacBook Pro too, not only on Sofia.
10. Ask every question before a build. Never overwrite an installer under an old name.

From an earlier plug-in (native) [disk: `plugin/MODULE.md`, `build.sh`, `test.sh`, `aax/`, `symphony/RECALL-PLUGIN-PLAN.md`]:
1. The core knows no host types; the shims know nothing about the core's insides. About 1,600 lines of shim for three formats (counted today).
2. One audio function shared by every format, and a tripwire test that fails if the audio thread allocates or locks.
3. Universal objects, `-mmacosx-version-min=12.0`, `-Wall -Wextra -Werror`, an exports list per bundle, a smoke test per bundle that needs no host.
4. Every refusal prints its reason and exits non-zero. Every failure path has a named log line.
5. The AAX library is compiled from the SDK's sources (no prebuilt library ships); the SDK path has a space, so flags go through a space-free link.
6. VST3 hosts call `setState` before `initialize`; state must be held until the plug-in is ready.
7. Gap: Artemis's shims were never run through auval or pluginval (its plan forbade them for agents). Beat Key closes that gap first (§8).

### A2. The decision, and why

| Need | JUCE (Zeropoint) | Native core + shims (Artemis) |
|---|---|---|
| AudioSuite whole-clip **Analyze** | JUCE's AAX wrapper has no analysis pass: 0 mentions of `HostProcessor` / `OptionalAnalysis` in `juce_audio_plugin_client_AAX.cpp` [disk]. AudioSuite there = Render, which rewrites the clip. Fixing it means carrying a patched JUCE forever. | The SDK has it: `AAX_CHostProcessor::AnalyzeAudio`, `AAX_eProperty_OptionalAnalysis`, example `DemoDelay_HostProcessor` [disk]. We own the describe code, so it is ours to add. |
| Parameters and automation | JUCE's main value. | Beat Key has almost none (bypass). The value goes unused. |
| The face | JUCE components or a WebView: key spelling, tempo text, Auto-Tune hand-off and the look get written a second time. | SwiftUI in an `NSHostingView`: the app's own Swift files and the house kit's Swift modules, one copy. |
| MIDI variant | Easy flags, but the forum reports the MIDI-effect flag breaking AAX (recon). | By hand per format; SDK examples `DemoMIDI_NoteOn`, `DemoMIDI_Transpose` [disk]. |
| pluginval 10 | Proven (Zeropoint VST3). | Not proven. Gated first (§8). |
| Builds | CMake; two products (arm and x86); pinned to an untagged JUCE commit. | Shell + clang; one universal bundle per format. |
| Licence | AGPLv3 option, fine (L5). | No framework licence at all (§L line 3). |
| Track record | Zeropoint ships all three formats to testers. | an earlier plug-in is built and signed in all three formats [disk]; how it behaves in hosts is the Artemis folder's to say. |

Choice: **native core + shims**. The analyzer core is JUCE-free either way. What is left is a pass-through effect with a small face and three format-specific features (AudioSuite Analyze, MIDI out, the realtime tap). JUCE helps with none of the three and blocks one. Its strength, parameters, is not needed. The face and the send code already exist in Swift in this repo.
The cost, stated plainly: hand-written VST3 and AU must pass validators that the Artemis shims never faced. §8 puts that gate before any feature work, so if it goes badly the loss is one step, and the core, the face and the sends are untouched by the answer.

Not chosen: AUv3 (runs out of process in a sandbox; AUv2 reaches Logic, Live and Artemis). CLAP (none of J's hosts). ARA (one ARA process per track; not worth it for a reader). iPlug2 (a whole framework for a plug-in with no parameters).

### A4. Realtime design

1. Audio thread (`process` in every format): copy input to output untouched, then push a mono downmix into a per-instance lock-free single-producer ring. No allocation, no lock, no log, no system call. If the ring is full it drops and bumps a counter; it never waits.
2. One worker thread per host process serves every Beat Key instance (low priority). It drains the rings, resamples to 44.1 kHz (key) and 11.025 kHz (tempo), and runs the same streaming logic as `LiveAnalyzer` in `bpm.py`: 12 s tempo window, 30 s key window, a reading every 2 s, the silence and song-boundary rules.
3. Results go to the face through an atomic snapshot. The face reads; it never calls into the audio thread.
4. Offline bounce: the host runs faster than real time, the ring drops, nothing blocks. A reading is not needed during a bounce.
5. AudioSuite: not the ring. The host hands the whole selection on its offline thread, and the core runs the file algorithm (`analyze_full`), so the result matches the app's result for the same audio.
6. The plug-in reads the host's tempo (VST3 process context, AU host callback, `AAX_ITransport`) to show the session tempo next to the detected one and to prove a SEND BPM landed (§S1).
7. Session state (a small versioned blob in the DAW session): the pin, the ×2 / ÷2 choice, the last reading. Reopening a session shows the last reading without playing.

### A5. Parity rule

The core is trusted only when it reproduces the Python outputs. Python stays the reference until §19.
- Goldens: for every file in `docs/research/key-bench`, `docs/research/bpm-bench` and a 20-file smoke set, the Python outputs as JSON (key top-3 with scores, pcp12, tuning cents, TempoCNN class per patch, global BPM, refined BPM), plus streaming readings for the smoke set.
- Pass = same key ranking and percentages, same TempoCNN class for every patch, refined BPM within 0.01, tuning within 0.5 cent, on every file. A miss is a bug in the port, never a new tolerance.
- The port must copy the awkward parts exactly: Essentia's FrameCutter noise on silent frames (`tempocnn_np.py` header), the unnormalised hann, the slaney mel bands, HPCP with whitening and the retune rule, Essentia's resampler quality (look it up in the wheel's source before choosing one).

- Universal arm64 + x86_64, macOS 12.0 minimum, built on the MacBook Pro (Xcode 27). Sofia (Intel, macOS 12.7.6) only runs it. Not Zeropoint's two-product scheme: that exists for side-by-side A/B names; a universal bundle also loads in x86-only Live 10.

Then, if `$BEATKEY_AAX_SIGN` (default `~/.config/beat-key/aax-sign.sh`, outside the repo, beside the Sparkle key) exists, the build runs it on the bundle and checks the result. ## §S. The two buttons

### S1. SEND BPM

Facts:
- No plug-in format lets a plug-in set the host's tempo. `AAX_ITransport` only reads tempo and can start or stop the transport [disk: `Interfaces/AAX_ITransport.h`]. PTSL has no tempo command [disk: `ProToolsDriver.swift` header]. Pro Tools and Logic take tempo through Accessibility, and that permission belongs to an app, not to code inside the DAW.
- The app already does all of it: `app/Sources/Orion/DAWSend/` (Pro Tools, Logic, Studio One by Accessibility; Live by its Remote Script; REAPER and Bitwig by their scripts; a MIDI file for the rest).

Design: one path, the app's. The plug-in asks, the app sends.
1. Extend the existing broadcast contract (`docs/protocol-beatkey-broadcast.md`, distributed notifications) with two names:
   - `com.jshriver.orion.send` (plug-in → app): `requestID`, `bpm` (as the face shows it, ×2 / ÷2 applied), `hostBundleID`, `hostPid`, `proto`.
   - `com.jshriver.orion.sent` (app → plug-in): `requestID`, `ok`, `message` (the one-line result the app's drivers already produce).
2. App side: a small listener beside `Broadcast.swift` maps `hostBundleID` to a `DAW` (`DAW.from`), builds a tempo-only `SendPayload`, and calls a new non-modal entry on `DAWSendController` (same drivers, same queue, same busy rule; the result goes back in `sent` instead of an alert). Setup and permission steps still show in the app, as today.
3. Plug-in side: press → post `send` → wait for `sent` (timeout 8 s) → show the app's line → read the host tempo and show "Session tempo 141.98" or "still 120.00". The read-back is the proof.
4. App not running: the plug-in opens it (bundle id `com.jshriver.orion`), waits for it, then sends. App not installed: the face says SEND BPM needs the Beat Key app, with the download link. Analysis and SEND AUTO-TUNE work without the app.
5. Host is Artemis: not a DAW in the app's list. The app answers by posting the existing `reading` notification with the plug-in's BPM, which is the contract Artemis's Beat Key button was written for. The Artemis side of that contract is unconfirmed (`docs/protocol-beatkey-broadcast.md` says so); confirming it is the Artemis folder's work.
6. Sandboxed hosts cannot post distributed notifications with a payload. Pro Tools and Logic are not sandboxed (`(private path)` §2.5, checked there 2026-11-05); Live 10 and Artemis are not either [disk: `codesign -d --entitlements` today]. Any host that is: the face says so and logs it.

### S2. SEND AUTO-TUNE

- Writes `~/Music/Audio Music Apps/Temp/Auto-Key.handoff`, the file Antares' own Auto-Key writes from inside a host, so every Auto-Tune Pro with Auto Key Detection on takes the key (`AutoTuneSend.swift`, `docs/research/send-to-daw.md` §4).
- The plug-in does this itself, with the same Swift code the app uses (moved into `BeatKeyShared`, one copy). No app needed.
- Key sent = the key in use (the pin if set, else the detector's first), Auto-Tune's spelling. Same content as the app writes today.
